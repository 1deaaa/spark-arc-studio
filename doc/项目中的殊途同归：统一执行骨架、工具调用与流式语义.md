# 项目中的殊途同归：统一执行骨架、工具调用与流式语义

更新时间：2026-03-11

## 1. 为什么要写这份文档

本项目里有很多看起来不同、实际非常相似的实现：

- 页面入口不同
- 协议不同
- 返回格式不同
- 执行对象不同

但仔细看，会发现它们在更高一层往往遵循相同的骨架。

这就是本项目非常重要的一种工程特征：

> **殊途同归。**

理解这一点，对于后续贡献者非常重要。因为很多“看起来不同”的能力，真正应该复用的是骨架和语义，而不是照着页面抄一份新实现。

---

## 2. 第一类“殊途同归”：Agent 基座与执行器思想

### 2.1 `SparkBaseAgent` 的统一价值

Agent 并不是一堆零散脚本，而是共享一层通信与工具执行基座。

这层基座负责：

- 上下文注入
- 提示词加载
- 工具绑定
- 工具执行
- 流式聊天输出

它的核心价值不在“替所有 Agent 长得一模一样”，而在于：

- 给每个 Agent 提供同一种工作方式
- 给导演调度与工具调用提供同一种接入面

### 2.2 不同 Agent，共享相似的执行骨架

不论是 Showrunner、ScriptWriter、Muse，还是 Style / Lorebook 相关能力，很多时候都会经过：

1. 构建 context
2. 执行 agent 或调用模型
3. 流式产出中间结果
4. 完成后写结果或触发副作用

这说明项目真正统一的不是“业务名字”，而是“执行骨架”。

---

## 3. 第二类“殊途同归”：工具调用统一了多种入口

### 3.1 rewrite / patch / 页面入口 / MCP 入口，本质都在操作同一类能力

项目中很多地方最终都指向同一种事情：

- 读取现有状态
- 修改文本
- 覆盖内容
- 写回项目

这些动作可能来自：

- 页面按钮
- 聊天工具调用
- MCP 工具
- 未来导演 Agent 调度

表面入口不同，但它们最后汇到的都是：

- 同一类内容改写语义
- 同一类落盘语义
- 同一类副作用语义

### 3.2 为什么工具调用是这一层的中心

页面入口适合人操作。

但对于：

- 导演 Agent
- MCP
- 未来 LUI

真正稳定的不是页面，而是工具调用名、参数 schema、结果语义。

所以从工程角度看，本项目越来越应该以“工具能力面”为中心，而不是以“页面入口”为中心。

---

## 4. 第三类“殊途同归”：多条生成链路的统一执行骨架

看起来不同的这些链路，其实都高度同构：

- 灵感扩展
- 梗概生成
- 节拍表生成
- 大纲生成
- 世界观生成
- 角色生成
- 风格分析
- ScriptWriter compose / feedback / bridge / auto-write

它们通常都能拆成：

1. 准备输入与上下文
2. 启动长时执行
3. 流式产出文本 / 进度 / 统计
4. 支持取消或断连
5. 完成后保存或收尾
6. 输出最终结果或错误终态

### 4.1 什么时候应该统一

应统一的是：

- 执行生命周期语义
- 取消模型
- 收尾模型
- 统计模型
- 可观察性

### 4.2 什么时候不应该硬统一

不应为了统一而硬改：

- 自然纯文本流
- 聊天专用协议
- 页面独有的业务细节状态机

统一应该落在“骨架和语义”层，而不是“协议表面长得完全一样”层。

---

## 5. 第四类“殊途同归”：前端统一运行时

前端现在最重要的统一点，不是某个页面，而是统一流式运行时。

### 5.1 核心思想

无论某条流来自：

- 纯文本 reader
- NDJSON
- SSE
- EventSource

最终都应该先被翻译成同一种“前端能理解的任务对象”。

### 5.2 统一运行时解决了什么

它统一了：

- loading
- progress
- chars / speed / elapsed
- cancel
- scope / target
- 结束 / 错误 / 中止处理

这意味着以后贡献者新增流式功能时，不应再优先复制某个页面的旧 reader 循环，而应优先复用统一运行时。

---

## 6. 第五类“殊途同归”：后端统一流式语义层

后端最近新增的一个重要方向，是给长时流补统一语义层。

### 6.1 这层不是强迫所有协议长一样

后端仍然允许：

- 纯文本流
- SSE
- NDJSON
- 聊天专用事件流

但对关键长时流，会逐步补上一层稳定 onXxx 语义。

### 6.2 统一的语义名

目前统一语义主要包括：

- `onStart`
- `onProgress`
- `onDelta`
- `onReasoningDelta`
- `onStats`
- `onToolStart`
- `onToolEnd`
- `onDone`
- `onError`
- `onCancelled`

注意：

这些是“统一消费语义”，不是要求上游原始字段必须同名。

---

## 7. 对贡献者的扩展规范

### 7.1 新增链路时，优先复用骨架

新增功能时先问：

- 这是已有能力的变体吗？
- 能否复用已有 context 构建方式？
- 能否复用已有流式运行时？
- 能否补到已有工具能力面，而不是额外发明一个页面私有逻辑？

### 7.2 先判断应该统一哪一层

新增功能不要默认“协议统一”，而应先判断：

- 应统一的是执行骨架？
- 工具能力面？
- 流式语义？
- 还是页面交互？

很多问题不是不能统一，而是统一层级放错了。

### 7.3 对不适合统一的地方保持克制

以下场景要避免生硬统一：

- 自然纯文本输出
- 已稳定运行的聊天专用协议
- 为人类用户体验服务的页面专用细节状态机

### 7.4 对适合统一的地方要主动收口

以下场景应主动收口：

- 长时任务 loading / cancel / stats
- 工具调用参数 schema
- 长时执行生命周期语义
- 执行完成后的副作用说明

---

## 8. 本项目架构的一个优势

本项目真正的优势，并不在于“所有东西表面长得完全一样”，而在于：

> **不同来源、不同页面、不同协议、不同 Agent，最后越来越能共享同一套执行骨架、工具能力面和流式语义。**

这让系统具备了非常好的扩展潜力：

- 它对页面扩展友好
- 对 Agent 自动化友好
- 对 MCP 暴露友好
- 对未来 LUI 非常友好

这也是后续贡献者最值得保护的一种工程气质：

> 不做表面统一，而做高层语义和执行骨架的统一。

---

## 9. 最终建议

如果后续贡献者要继续扩展项目，请尽量沿着下面这条路线思考：

1. 先找有没有已存在的执行核心
2. 再找能不能做成工具门面
3. 再判断需不需要流式语义补层
4. 最后才考虑页面如何承接

这样做，既能保持现有系统的稳定，又能继续放大本项目“殊途同归”的架构优势。
