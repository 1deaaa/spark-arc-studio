# SparkArc 客户端热更新与版本治理方案

## 1. 背景

当前 SparkArc 的浏览器端与 Tauri 客户端共享同一套前端代码，但发布形态不同：

- 浏览器端：由后端直接托管 `client/dist`，服务端一更新，用户访问即看到最新前端。
- 客户端端：Windows / macOS / Linux / Android 打包时把当时的 `client/dist` 一并塞进安装包，因此安装包发布后，前端内容被“冻结”。

这会导致一个典型问题：

- 你更新了服务端和 Web 前端。
- 浏览器用户立即拿到最新界面。
- 已安装客户端用户仍停留在旧前端，除非重新下载安装包。

这会把“前端发布”错误地绑定到“原生壳升级”，后续维护成本会越来越高。

## 2. 目标

设计一套双层版本体系：

1. **前端版本独立发布**：大多数 UI / 页面 / 业务交互更新无需重新发 4 个客户端安装包。
2. **壳层版本独立升级**：只有涉及原生能力、权限、WebView 行为、安装器修复时，才要求用户升级客户端。
3. **兼容性可控**：服务端能明确判断某个客户端是否还能继续用，是否必须升级。
4. **复用现有公告系统**：把“人读的升级说明”挂到现有公告，不再重复造内容后台。
5. **尽量贴合现有架构**：优先复用当前的服务地址配置、健康检查、公告弹窗和后端统一托管前端能力。

## 3. 现状判断

从仓库看，当前客户端技术形态已经很明确：

- Tauri 配置将生产前端固定为本地打包资源：`client/src-tauri/tauri.conf.json`
- 客户端已有“服务地址”配置能力：`client/src/components/user/LoginPage.vue`
- 前端请求基于可配置的 API Base URL：`client/src/services/apiClient.ts`
- 后端已托管浏览器版前端入口：`server/app.py`
- 公告系统已完整可用：`server/core/notice_mgr.py`、`/api/system/notice`、`client/src/components/share/AnnouncementModal.vue`

这意味着：

- 你已经具备“客户端连接任意服务端实例”的基础能力。
- 真正缺少的是“客户端壳层启动后，优先加载服务端前端”的运行时策略，以及一套机器可读的版本协商接口。

## 4. 核心方案

推荐采用：

**本地壳层 + 远端前端 + 兼容性协商 + 公告联动**

把客户端拆成两层：

### 4.1 壳层（Native Shell）

职责尽量小，只负责：

- 启动 WebView
- 保存服务地址
- 做健康检查
- 拉取运行时清单（manifest）
- 判断是否允许进入服务端前端
- 在必须时展示“升级客户端 / 服务不可用 / 公告说明”

壳层不再承载完整业务前端，只保留一个很薄的“启动器 / 配置页 / 降级页”。

### 4.2 前端（Remote Web App）

真正的业务 UI 继续由服务端托管的 `client/dist` 提供。

客户端启动后：

1. 读取本地保存的服务地址。
2. 请求服务端运行时清单。
3. 若兼容，则 WebView 直接加载该服务地址下的正式前端。

这样以后：

- 改页面、改交互、改业务逻辑，只需要部署服务端的新 `client/dist`
- 已安装客户端无需重新打包
- 浏览器和客户端天然保持同一套前端

## 5. 为什么这是最适合 SparkArc 的方案

因为 SparkArc 客户端本来就不是一个强离线 App，而是一个“连接后端实例”的工作台：

- 登录前已经要求配置服务地址
- 数据、Agent、流式任务、公告、项目内容都依赖服务端
- 浏览器端和 App 端本质上应该是同一套前端运行在不同容器里

既然业务天然依赖服务端，那么“前端跟随服务端版本”就是最省维护成本的正解。

## 6. 版本模型

建议显式区分 3 个版本号：

### 6.1 `shell_version`

客户端壳层版本，例如：

- `0.1.0`
- `0.2.0`

表示安装包本身的版本。

### 6.2 `web_version`

服务端当前托管的前端版本，例如：

- `2026.04.22.1`
- `1.14.3`

表示浏览器端和客户端最终要加载的业务前端版本。

### 6.3 `api_version` 或兼容区间

用于壳层和服务端协商最低兼容要求，例如：

- `min_shell_version`
- `recommended_shell_version`
- `min_api_level`

建议首版先用最简单的两个字段：

- `min_shell_version`
- `recommended_shell_version`

足够实用。

## 7. 新增一个“机器可读”的运行时清单接口

不要拿公告文本做兼容性判断。公告适合给人看，不适合程序判断。

建议新增：

- `GET /api/system/client-runtime`

返回示例：

```json
{
  "success": true,
  "shell_min_version": "0.1.0",
  "shell_recommended_version": "0.2.0",
  "web_version": "2026.04.22.1",
  "web_entry_url": "https://your-server.example.com/",
  "upgrade_required": false,
  "upgrade_notice_id": "xxxx-xxxx",
  "release_channel": "stable"
}
```

### 字段职责

- `shell_min_version`
  - 低于此版本的客户端必须升级，否则禁止继续进入业务前端。
- `shell_recommended_version`
  - 低于此版本时允许继续使用，但提示建议升级。
- `web_version`
  - 当前服务端前端版本，仅用于展示和诊断。
- `web_entry_url`
  - 客户端应加载的正式入口。
- `upgrade_required`
  - 服务端可直接给出最终判断，减少客户端重复逻辑。
- `upgrade_notice_id`
  - 关联现有公告系统，用于展示升级说明、变更说明、下载链接等。

## 8. 公告系统怎么复用

现有公告系统已经很适合承载“人类可读的升级说明”。

建议把职责拆开：

- **运行时清单接口**：判断能不能进、要不要升级
- **公告系统**：展示升级内容、变更日志、注意事项、下载链接

推荐给公告增加可选元数据字段：

- `kind`: `general` / `client_upgrade` / `maintenance`
- `target_platforms`: `["windows", "macos", "linux", "android"]`
- `min_shell_version`
- `cta_label`
- `cta_url`

如果你暂时不想改公告存储结构，也可以先走轻量方案：

- 继续用现有 `title + content`
- 在 `client-runtime` 接口里只返回 `upgrade_notice_id`
- 客户端再调用现有公告接口展示对应公告内容

这已经足够把两套系统联起来。

## 9. 客户端启动流程

推荐流程如下：

1. 启动本地壳层。
2. 读取本地保存的服务地址。
3. 调用 `/health`，确认服务在线。
4. 调用 `/api/system/client-runtime`。
5. 比较本地 `shell_version` 与服务端要求：
   - 若低于 `shell_min_version`：
     - 不进入业务前端
     - 展示强制升级页
     - 如有 `upgrade_notice_id`，展示对应升级公告
   - 若低于 `shell_recommended_version`：
     - 允许进入
     - 弹出“建议升级”公告
   - 若兼容：
     - 直接加载 `web_entry_url`
6. 后续业务全部跑服务端托管的最新前端。

## 10. 建议的三种运行模式

### 模式 A：纯远端模式（推荐默认）

客户端总是加载服务端前端。

优点：

- 维护最省
- 浏览器和客户端前端完全一致
- 发版链路最简单

缺点：

- 服务端挂了时，客户端业务页面也无法进入

但这对 SparkArc 来说通常可以接受，因为核心能力本就强依赖服务端。

### 模式 B：本地壳 + 远端失败回退本地只读页（推荐）

这是最平衡的方案。

正常情况：

- 加载远端前端

失败情况：

- 显示本地内置的启动页 / 错误页 / 服务地址配置页 / 公告页

这样用户不会看到白屏。

### 模式 C：完整本地前端 + 远端资源热更（不推荐作为首选）

即继续让 App 内置完整前端，再做增量资源更新、资源缓存、签名校验、版本回滚。

这套方案复杂很多，适合强离线产品，不适合当前 SparkArc 的真实需求。

对于你现在的项目，会明显增加维护面：

- 资源清单
- 包签名
- 缓存目录
- 热更失败回滚
- 多平台一致性
- WebView 缓存污染

除非你后面明确要做强离线创作，不然不建议先上。

## 11. 发布策略

建议以后把发布拆成两条线：

### 11.1 日常发布：只发服务端

适用场景：

- 页面改动
- 前端 bug 修复
- 新功能入口
- Agent 业务流程调整
- 流式交互优化

操作：

- 构建新 `client/dist`
- 部署服务端
- 所有浏览器端和客户端用户自动拿到最新前端

### 11.2 低频发布：发客户端安装包

适用场景：

- 新增原生能力
- 窗口行为变更
- 权限调整
- WebView / Tauri 层问题修复
- 启动器能力升级

操作：

- 发布新的 Windows / macOS / Linux / Android 安装包
- 通过 `client-runtime` 要求最低壳层版本
- 通过公告系统给出升级说明

## 12. 建议的兼容策略

### 12.1 默认原则

- 前端更新尽量不依赖新壳层
- 壳层尽量向后兼容旧服务端
- 只有当新前端确实依赖新原生能力时，才提升 `shell_min_version`

### 12.2 强制升级只用于这几类情况

- 登录流程或安全模型变化
- Tauri 插件/权限变化
- 远端加载策略变化
- 已知旧壳层存在严重崩溃或白屏问题

不要把普通功能迭代也做成强制升级，否则用户体验会很差。

## 13. 对现有代码的最小改造建议

### 13.1 客户端侧

保留：

- `client/src/components/user/LoginPage.vue`
- `client/src/services/apiClient.ts`

新增或调整：

- 增加一个本地“启动器页”，专门做：
  - 服务地址读取
  - 健康检查
  - 拉取 `client-runtime`
  - 判断是否进入远端前端
- Tauri 壳层默认只加载这个启动器页
- 启动器页通过 `window.location` 或壳层导航切入远端正式前端

### 13.2 服务端侧

新增：

- 一个运行时清单管理模块，例如：
  - `server/core/client_runtime_mgr.py`
- 一个接口：
  - `GET /api/system/client-runtime`

复用：

- 现有 `notice_mgr.py`
- 现有 `/api/system/notice`

### 13.3 公告系统侧

第一阶段可不改数据结构，只做弱耦合复用。

第二阶段若要更精细化运营，再为公告补充：

- 平台
- 升级类型
- CTA 链接
- 最低壳层版本

## 14. 下载链接与商店分发

如果未来你希望壳层升级也更省心，建议再统一一个“下载入口”配置：

- Windows：安装包下载地址
- macOS：安装包下载地址
- Linux：安装包下载地址
- Android：APK / 商店地址

这部分最好也从服务端清单接口返回，而不是写死在客户端里。

这样公告里只负责说明：

- 为什么升级
- 升级了什么

实际下载按钮从清单接口拿平台对应链接。

## 15. 风险与注意事项

### 15.1 远端前端必须和服务端同源或稳定跨域

最省事的做法仍然是：

- 业务前端继续由 SparkArc 后端自己托管
- 客户端只加载用户配置的那个服务地址首页

这样：

- 登录态
- API 相对路径
- 资源路径
- 分享路由

都会最自然。

### 15.2 不要把“公告”当成兼容真相源

公告是给人看的。
兼容判断一定要走独立的 manifest / runtime 接口。

### 15.3 客户端要有“回不去业务页时”的本地兜底页

否则一旦远端服务不可用，用户会看到白屏或循环跳转。

### 15.4 WebView 缓存策略要控制

既然客户端要加载远端前端，就要避免 WebView 因缓存长期保留旧资源。
前端静态资源仍建议保留带 hash 的构建产物，这样服务端发布后浏览器和 App 都能自然拿到新资源。

## 16. 推荐实施顺序

### 第一阶段：先解决“更新不到前端”的核心痛点

1. 新增 `/api/system/client-runtime`
2. Tauri 客户端增加启动器页
3. 客户端兼容时直接加载服务端首页
4. 不兼容时展示升级页
5. 升级页复用现有公告系统内容

这一阶段做完，问题基本就解决了。

### 第二阶段：把升级运营体验做完整

1. 公告增加升级类型和下载链接元数据
2. 客户端支持“建议升级”与“强制升级”两种提示
3. 服务端维护平台下载地址

### 第三阶段：再考虑壳层自动升级

如果后面你觉得有必要，再补：

- 桌面端自动更新
- Android 应用内升级或商店跳转

这不是首阶段必需项。

## 17. 最终建议

对 SparkArc，最值得做的不是“把 4 个客户端也做成复杂热更新系统”，而是：

**把客户端降级为稳定壳层，把业务前端彻底回归服务端托管。**

这是维护成本最低、与你当前架构最一致、也最能复用现有公告系统的方案。

一句话总结：

- **前端更新跟服务端走**
- **壳层更新按需低频发**
- **兼容判断靠 runtime manifest**
- **升级说明复用现有公告系统**

这样你后面维护的不是“浏览器 + 4 套冻结前端”，而是：

- 1 套服务端前端发布线
- 1 套低频客户端壳发布线

复杂度会明显下降。
