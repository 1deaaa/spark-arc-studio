# 项目中的殊途同归：统一执行骨架、工具调用与流式语义

更新时间：2026-03-11

## 1. 为什么要写这份文档

本项目里有很多看起来不同、实际非常相似的实现：

- 页面入口不同
- 协议不同
- 返回格式不同
- 执行对象不同

但仔细看，会发现它们在更高一层往往遵循相同的骨架。

这就是本项目非常重要的一种工程特征：

> **殊途同归。**

理解这一点，对于后续贡献者非常重要。因为很多“看起来不同”的能力，真正应该复用的是骨架和语义，而不是照着页面抄一份新实现。

---

## 2. 第一类“殊途同归”：Agent 基座与执行器思想

### 2.1 `SparkBaseAgent` 的统一价值

Agent 并不是一堆零散脚本，而是共享一层通信与工具执行基座。

这层基座负责：

- 上下文注入
- 提示词加载
- 工具绑定
- 工具执行
- 流式聊天输出

它的核心价值不在“替所有 Agent 长得一模一样”，而在于：

- 给每个 Agent 提供同一种工作方式
- 给导演调度与工具调用提供同一种接入面

### 2.2 不同 Agent，共享相似的执行骨架

不论是 Showrunner、ScriptWriter、Muse，还是 Style / Lorebook 相关能力，很多时候都会经过：

1. 构建 context
2. 执行 agent 或调用模型
3. 流式产出中间结果
4. 完成后写结果或触发副作用

这说明项目真正统一的不是“业务名字”，而是“执行骨架”。

---

## 3. 第二类“殊途同归”：工具调用统一了多种入口

### 3.1 rewrite / patch / 页面入口 / MCP 入口，本质都在操作同一类能力

项目中很多地方最终都指向同一种事情：

- 读取现有状态
- 修改文本
- 覆盖内容
- 写回项目

这些动作可能来自：

- 页面按钮
- 聊天工具调用
- MCP 工具
- 未来导演 Agent 调度

表面入口不同，但它们最后汇到的都是：

- 同一类内容改写语义
- 同一类落盘语义
- 同一类副作用语义

### 3.2 为什么工具调用是这一层的中心

页面入口适合人操作。

但对于：

- 导演 Agent
- MCP
- 未来 LUI

真正稳定的不是页面，而是工具调用名、参数 schema、结果语义。

所以从工程角度看，本项目越来越应该以“工具能力面”为中心，而不是以“页面入口”为中心。

---

## 4. 第三类“殊途同归”：多条生成链路的统一执行骨架

看起来不同的这些链路，其实都高度同构：

- 灵感扩展
- 梗概生成
- 节拍表生成
- 大纲生成
- 世界观生成
- 角色生成
- 风格分析
- ScriptWriter compose / feedback / bridge / auto-write

它们通常都能拆成：

1. 准备输入与上下文
2. 启动长时执行
3. 流式产出文本 / 进度 / 统计
4. 支持取消或断连
5. 完成后保存或收尾
6. 输出最终结果或错误终态

### 4.1 什么时候应该统一

应统一的是：

- 执行生命周期语义
- 取消模型
- 收尾模型
- 统计模型
- 可观察性

### 4.2 什么时候不应该硬统一

不应为了统一而硬改：

- 自然纯文本流
- 聊天专用协议
- 页面独有的业务细节状态机

统一应该落在“骨架和语义”层，而不是“协议表面长得完全一样”层。

---

## 5. 第四类“殊途同归”：前端统一运行时

前端现在最重要的统一点，不是某个页面，而是统一流式运行时。

### 5.1 核心思想

无论某条流来自：

- 纯文本 reader
- NDJSON
- SSE
- EventSource

最终都应该先被翻译成同一种“前端能理解的任务对象”。

### 5.2 统一运行时解决了什么

它统一了：

- loading
- progress
- chars / speed / elapsed
- cancel
- scope / target
- 结束 / 错误 / 中止处理

这意味着以后贡献者新增流式功能时，不应再优先复制某个页面的旧 reader 循环，而应优先复用统一运行时。

---

## 6. 第五类“殊途同归”：后端统一流式语义层

后端最近新增的一个重要方向，是给长时流补统一语义层。

### 6.1 这层不是强迫所有协议长一样

后端仍然允许：

- 纯文本流
- SSE
- NDJSON
- 聊天专用事件流

但对关键长时流，会逐步补上一层稳定 onXxx 语义。

### 6.2 统一的语义名

目前统一语义主要包括：

- `onStart`
- `onProgress`
- `onDelta`
- `onReasoningDelta`
- `onStats`
- `onToolStart`
- `onToolEnd`
- `onDone`
- `onError`
- `onCancelled`

注意：

这些是“统一消费语义”，不是要求上游原始字段必须同名。

---

## 7. 对贡献者的扩展规范

### 7.1 新增链路时，优先复用骨架

新增功能时先问：

- 这是已有能力的变体吗？
- 能否复用已有 context 构建方式？
- 能否复用已有流式运行时？
- 能否补到已有工具能力面，而不是额外发明一个页面私有逻辑？

### 7.2 先判断应该统一哪一层

新增功能不要默认“协议统一”，而应先判断：

- 应统一的是执行骨架？
- 工具能力面？
- 流式语义？
- 还是页面交互？

很多问题不是不能统一，而是统一层级放错了。

### 7.3 对不适合统一的地方保持克制

以下场景要避免生硬统一：

- 自然纯文本输出
- 已稳定运行的聊天专用协议
- 为人类用户体验服务的页面专用细节状态机

### 7.4 对适合统一的地方要主动收口

以下场景应主动收口：

- 长时任务 loading / cancel / stats
- 工具调用参数 schema
- 长时执行生命周期语义
- 执行完成后的副作用说明

---

## 8. reasoning / think 兼容层的标准接入方式

这是最近最需要统一收口的一层，因为许多 OpenAI 兼容平台虽然已经把推理放进
`reasoning_content` / `reasoning` 之类字段，但仍有少量中转会把
`<think>...</think>` 或 `<thinking>...</thinking>` 直接写进正文开头。

如果这类文本被页面或路由直接透传：

- 前端正文会被污染
- 纯文本流会把 think 标签显示给用户
- 各页面不得不自己写一套标签解析器补救

这不是正确的职责分配。

### 8.1 统一原则

本项目的标准原则现在应明确为：

1. **后端负责兼容 reasoning**
2. **前端只消费干净正文与结构化 reasoning 事件/字段**
3. **禁止把 think 标签解析责任下放给页面**

也就是说：

- 聊天/事件流：后端拆成 `reasoning_delta` 与可见正文
- 纯文本流：后端至少保证正文已经被净化，不允许把 think 标签原样传给前端

### 8.2 应优先复用的适配层

统一入口在：

- `server/llm/agen_matchbox/reasoning_compat.py`

其中常用能力包括：

- `extract_reasoning_text_from_message()`
  - 从 LangChain/OpenAI message 或 chunk 中提取 reasoning 文本
- `extract_text_content_from_message()`
  - 从 message 或 chunk 中提取用户可见正文
- `extract_visible_text_from_plain_text()`
  - 对纯文本做可见正文净化，剥离开头 think 块
- `extract_reasoning_text_from_plain_text()`
  - 对纯文本提取开头 think 块中的 reasoning
- `PrefixReasoningStreamParser`
  - 对流式纯文本做“仅开头 think 块”的状态机拆分

### 8.3 `PrefixReasoningStreamParser` 的适用规则

这个解析器不是“全文到处扫标签”，而是更严格的前缀规则：

- 只在**正文尚未开始前**识别 `<think>/<thinking>`
- 一旦正文开始，后续内容全部视为用户可见正文
- flush 时如果闭合标签并未完整到达，不会把残缺闭合标签写进正文

这是因为本项目对实际兼容场景的判断是：

> 某些中转大模型把 think 标签写进正文时，通常只会出现在正文一开始，不会在正文中段再次出现。

### 8.4 新增后端链路时该怎么接

#### 场景 A：聊天 / NDJSON / 事件流

优先做法：

1. 从原始 chunk 中调用：
   - `extract_reasoning_text_from_message(chunk)`
   - `extract_text_content_from_message(chunk)`
2. reasoning 用独立事件输出
3. visible text 用正文事件输出

示意：

```python
for chunk in llm.stream(messages):
    reasoning = extract_reasoning_text_from_message(chunk)
    if reasoning:
        yield {"event": "reasoning_delta", "text": reasoning}

    content = extract_text_content_from_message(chunk)
    if content:
        yield {"event": "assistant_delta", "text": content}
```

#### 场景 B：纯文本流

优先做法：

1. 创建一个 `PrefixReasoningStreamParser()`
2. 每个 chunk 进入 parser
3. 只把 `visible` 往外发
4. flush 时补发剩余的可见正文

示意：

```python
parser = PrefixReasoningStreamParser()
for chunk in llm.stream(messages):
    raw = getattr(chunk, "content", "")
    if not raw:
        continue
    _, visible = parser.push(raw)
    if visible:
        yield visible

_, trailing_visible = parser.flush()
if trailing_visible:
    yield trailing_visible
```

### 8.5 不推荐的写法

以下写法应尽量消除：

```python
for chunk in llm.stream(messages):
    if chunk.content:
        yield chunk.content
```

或者：

```python
return response.content
```

这类代码的问题是：

- 默认信任上游 `content` 已经是干净正文
- 一旦网关把 think 标签直接塞进 content，就会把污染直接扩散到前端

### 8.6 前端约束

前端可以保留兼容工具用于历史兜底，但**不应再把它当主链路依赖**。

新增功能时，前端不应默认：

- 手动解析 `<think>`
- 手动拆正文/推理
- 页面私有地补一层标签清洗

正确做法是：

- 聊天流直接消费后端提供的 reasoning 事件
- 纯文本流直接显示后端净化后的正文

### 8.7 对贡献者的执行要求

以后新增流式后端能力时，请先自查：

- 有没有直接透传 `chunk.content`？
- 有没有把 `response.content` 原样返回？
- 纯文本链路是否已接 `PrefixReasoningStreamParser`？
- 聊天/事件链路是否已拆 reasoning 与 visible text？
- 前端是否仍在依赖页面私有 think 解析？

如果答案里出现“是”，应优先回到 `reasoning_compat.py` 收口，而不是继续在页面层打补丁。

---

## 9. 本项目架构的一个优势

本项目真正的优势，并不在于“所有东西表面长得完全一样”，而在于：

> **不同来源、不同页面、不同协议、不同 Agent，最后越来越能共享同一套执行骨架、工具能力面和流式语义。**

这让系统具备了非常好的扩展潜力：

- 它对页面扩展友好
- 对 Agent 自动化友好
- 对 MCP 暴露友好
- 对未来 LUI 非常友好

这也是后续贡献者最值得保护的一种工程气质：

> 不做表面统一，而做高层语义和执行骨架的统一。

---

## 10. 最终建议

如果后续贡献者要继续扩展项目，请尽量沿着下面这条路线思考：

1. 先找有没有已存在的执行核心
2. 再找能不能做成工具门面
3. 再判断需不需要流式语义补层
4. 最后才考虑页面如何承接

这样做，既能保持现有系统的稳定，又能继续放大本项目“殊途同归”的架构优势。
