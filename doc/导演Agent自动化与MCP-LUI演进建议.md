# 导演 Agent 自动化与 MCP 向 LUI 演进建议

更新时间：2026-03-11

## 1. 这份文档要回答的问题

本项目未来的目标，并不只是让页面里的按钮越来越多，而是要让：

1. 导演 Agent 能按步骤调度多条执行链路
2. MCP 能稳定暴露这些能力给外部调用方
3. LUI（自然语言用户界面）能通过一句话精准命中某个能力并启动对应执行链

换句话说：

> 我们真正要建设的，不是“更多页面入口”，而是“更多可被调度的能力单元”。

---

## 2. 核心判断：未来应以工具调用为中心组织能力

对于导演 Agent、MCP、LUI 来说，最重要的不是页面入口，也不是某个具体按钮，而是：

- 能力名是否稳定
- 参数契约是否稳定
- 执行过程是否可观察
- 执行过程是否可取消
- 完成语义是否稳定
- 副作用是否明确

因此，未来系统的组织中心应当是：

### 2.1 工具调用（Tool Call）

也就是把关键执行链路逐步提升为：

- 可被 Agent 调用的工具
- 可被 MCP 暴露的工具
- 可被导演调度的工具

### 2.2 页面入口只是工具的一种调用来源

页面按钮、导演 Agent、MCP、未来 LUI，不应彼此抢夺“主入口”地位。

更合理的结构是：

1. **执行核心层**：真正负责生成、流式输出、落盘、取消、收尾
2. **工具门面层**：把执行核心封装成统一的可调度能力
3. **页面入口层**：面向用户手动触发
4. **导演 / MCP 入口层**：面向程序化调度与自然语言调度

这样做的好处是：

- 页面体验不被破坏
- Agent 与 MCP 获得统一能力面
- 后续新增调用源时，不必重写执行链本身

---

## 3. 当前系统已经具备的基础

### 3.1 工具定义层已经存在

当前项目已经有统一工具定义模块：

- `server/agents/agent_tools.py`

这里已经体现出明显的 tool-first 倾向：

- 世界观重写
- 角色重写 / 更新
- 梗概重写
- 节拍表重写
- 大纲重写
- 剧本重写
- 灵感捕获与回写
- patch 类局部修改工具

这说明系统本来就不是“页面驱动一切”，而是已经具备“能力被封装成工具”的架构基因。

### 3.2 Agent 通讯层已经是 tool-call 中心

当前 Agent 通讯层在流式聊天中已经以工具调用为核心：

- 模型先输出 tool call 意图
- 系统发出 `tool_intent_started`
- 实际执行工具后发出 `tool_exec_started` / `tool_exec_finished`
- 工具结果再被回注到对话流中

这说明导演 Agent 将来要做 orchestration，并不需要另起炉灶，只需要把“能被调度的能力面”继续扩出来。

### 3.3 前后端统一流式语义已经开始成型

当前前端统一运行时已经能承接：

- 全局 loading
- 进度文案
- 实时统计
- 可取消
- 定向 scope / target

后端也已经开始补统一 onXxx 语义。

这意味着未来工具调用不再只是“返回一段文本”，而是能返回“一个有生命周期的执行过程”。

这对导演自动化和 LUI 至关重要。

---

## 4. 下一阶段最值得推进的方向

### 4.1 把“关键执行链路”提升成工具门面

重点不在于把所有路由都替换掉，而在于：

- 保留现有路由
- 保留现有页面入口
- 再向上增加一层可被调度的工具门面

优先建议提升的链路：

1. ScriptWriter compose
2. ScriptWriter feedback
3. bridge
4. style analyze
5. auto-write
6. synopsis / beat / outline
7. worldview generate / character generate

这些链路应逐步具备：

- 稳定工具名
- 清晰参数 schema
- 流式执行语义
- 可取消能力
- 明确副作用

### 4.2 给工具建立统一分类模型

建议把工具分成三类：

#### A. 立即执行型工具

特点：
- 快速完成
- 通常同步返回
- 直接落盘或直接返回文本

例如：
- rewrite / patch / save 类工具

#### B. 长时生成型工具

特点：
- 有持续进度
- 可能持续产出文本
- 可取消
- 可能中途落盘或最终落盘

例如：
- synopsis / outline / compose / auto-write / style analyze

#### C. 调度型工具

特点：
- 不直接产出最终内容
- 负责决定调用哪个下层能力
- 更适合导演 Agent 作为 orchestrator 使用

未来导演 Agent 很可能需要这一类工具来完成跨链编排。

### 4.3 把 onXxx 生命周期正式提升成“工具执行语义”

目前 onXxx 更多是流式语义。

下一阶段更理想的目标是：

- `onStart`：工具任务已接受并开始执行
- `onProgress`：工具处于某个执行阶段
- `onDelta`：工具产出正文增量
- `onStats`：工具实时统计
- `onDone`：工具执行完成
- `onError`：工具执行失败
- `onCancelled`：工具被取消

这样一来，导演 Agent 和 MCP 就不需要理解具体页面，也不需要理解底层协议细节，它们只需要理解“工具执行生命周期”。

### 4.4 明确每个工具的副作用语义

未来工具层必须明确说明：

- 该工具是否会落盘
- 该工具落盘到哪里
- 该工具完成后是否已经写入项目状态
- 该工具失败后是否可能有部分副作用

如果没有这层说明，导演 Agent 很难稳定编排多步流程。

---

## 5. 什么不能为了 tool-first 而生硬统一

tool-first 不等于“一切长得都一样”。

以下几类能力需要保留差异化：

### 5.1 自然纯文本流

像梗概、节拍、大纲、Muse、世界观这类，有些流天然更适合持续吐文本。

这类能力不必为了“统一协议”而强改成复杂结构化事件流。

更合理的做法是：

- 保留自然文本输出
- 在更高层补执行语义
- 让工具门面声明这是一条 `plain_text_stream` 能力

### 5.2 聊天专用事件协议

聊天流已经有较成熟的专用协议，例如：

- `assistant_delta`
- `reasoning_delta`
- `tool_*`

这套协议已经天然服务于 Agent 对话，不应为了“表面统一”而强行抹平。

更合理的做法是：

- 保留其领域内协议
- 在更高层映射为统一工具执行语义

---

## 6. 一条最推荐的落地方向

如果未来要正式启动导演 Agent 自动化与 MCP / LUI 接入，推荐按以下顺序推进：

1. 把关键生成链路封装成工具门面
2. 给每个工具补清晰 schema 与副作用说明
3. 让工具运行过程统一映射到 onXxx 生命周期
4. 页面入口继续保留，只是改为调用同一个执行核心
5. 导演 Agent 再从“直接记忆链路知识”升级为“只调工具能力面”

这样可以最大化复用现有系统，又不会破坏当前用户手动触发体验。

---

## 7. 最终判断

这轮整改最大的价值，不只是统一了页面体验，而是让系统开始具备下面这件事的基础：

> 让导演 Agent、MCP、未来 LUI，都能把项目里的复杂执行链当成一组稳定、可观察、可取消、可组合的工具能力来调用。

只要后续继续沿着“工具门面 + 执行核心 + 统一执行语义”推进，这个目标是现实可达的。
