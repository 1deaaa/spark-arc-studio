## 二、 超长上下文演进对“长篇小说写作上下文拼装思路”的重大影响

百万级大窗口上下文的成熟，并没有让“记忆管理与 RAG”失去价值，而是彻底改变了上下文的拼装哲学。技术演进主要带来以下两个维度的深远影响：

### 1. 从“极致物理裁剪”向“分层缓存策略 (Prompt Caching)”转变
*   **过去（4K-16K 窗口时代）**：受制于狭小的空间，上下文装配必须极其抠门，频繁删减前文，甚至被迫将全量角色卡片裁剪得残缺不全，导致模型丢失设定（吃书）。
*   **现在（256K-1M 窗口时代）**：我们有足够的空间将**整部小说的世界观设定、完整大纲、全量 50+ 个角色的详细 txt 卡片**，甚至前几章的数万字正文一次性塞入大模型。
*   **工程最优解：利用 Prompt Caching 进行低成本静态锚定**
    主流厂商（Anthropic, DeepSeek, OpenAI, Google）在 2026 年均已原生支持 **Prompt Caching（提示词缓存）** 机制。这要求我们将上下文解构为“静态前缀 + 动态尾部”：
    1.  **静态缓存区 (System Prompt)**：将静态的、极少发生改变的世界观文本、全量角色档案卡片、全书梗概大纲放在 System Message 中，作为**稳定前缀**。只要前缀文本不变，后续连续生成时，API 自动命中缓存（Cache Hit），**缓存的计费折扣通常高达 50% 至 90%**，且大幅削减了首 Token 延迟。
    2.  **动态生成区 (User Message)**：将最近一章的前文、当前的 Guidance（写作指导）、以及 GraphRAG 提取的即时线索放在 User Message 的最尾部。这些随着写作步骤动态变化，不破坏上游的静态缓存块。

```
LLM Context Window (1M Tokens)
┌───────────────────────────────────────────────────────────────────────────────┐
│ System Message [稳定前缀 - 自动命中 Prompt Caching (费用折减 50%-90%)]          │
│ ├─ 世界观设定.txt (20K tokens)                                                │
│ ├─ 全量角色设定库 [cid].txt拼合 (50K tokens)                                   │
│ └─ 完整大纲与结局 (10K tokens)                                                │
├───────────────────────────────────────────────────────────────────────────────┤
│ User Message [动态尾部 - 频繁变化，不破坏缓存前缀]                            │
│ ├─ 最近一章已写前文 (10K tokens)                                              │
│ ├─ GraphRAG 提取的当前冲突事实与伏笔 (2K tokens)                               │
│ └─ [当前场景写作指导与 POV 锁定指令] (1K tokens)                               │
└───────────────────────────────────────────────────────────────────────────────┘
```

### 2. “Lost in the Middle”注意力缺失依然存在，Graph RAG 依旧不可替代
即便物理窗口达到了 1M，大模型对“夹在超长上下文中间”的信息召回率（Attention Retrieve Performance）依旧会发生退化。
*   **海量设定下的噪声污染**：将 50 个角色的详细卡片全量灌入，即使命中缓存，大模型在写 John 的场景时，仍会受到另外 49 个无关角色卡片文字的干扰（Attention Dispersion），容易引发人设混淆（OOC）。
*   **Graph RAG 与 Ad-hoc 注入依然是黄金法则**：在 2026 年，最成熟的架构依然是结合大窗口的容纳力进行“Ad-hoc 动态实体卡片提取”：在大窗口中缓存大纲和主线，但**仅提取出场角色的详细档案注入**。而对于长距离的特定伏笔（如第 2 章发生的抢玉事件），依旧需要通过 **Graph RAG 进行高精度索引和定点拉取**。
