# 基于前沿进展的 SparkArc 创作流重构建议书

本建议书基于 PLOTTER (2026)、SCORE (2025) 以及 2026 年大上下文模型与 Prompt Caching 的最新突破，针对 SparkArc 项目现行架构存在的上下文与连贯性短板，提出以下落地的重构设计建议。

---

## 💡 建议一：将现有 GraphRAG 升级为“实体-事件时序双图 (E2RAG)”与“惰性构建 (LazyGraphRAG)”

### 1. 解决痛点
解决“当关键的两个人物被切到了物理开头和尾部的分片，传统的无向图谱 Graph RAG 会因为丢失时间线，发生因果倒置（吃未来设定）”的致命痛点。同时解决“只要作者反悔修改前文，GraphRAG 就必须对全书进行昂贵的离线重建总结，导致 Token 费用飙升”的落地难题。

### 2. 重构设计
1.  **升级为双图存储 (E2RAG)**：
    *   在后台 NetworkX 表征中，将“人物固有属性（Entity Subgraph）”与“时序情节事件（Event DAG）”进行物理分离。
    *   事件节点按照物理章节时序（Chapter -> Scene）以有向边串联，事件节点上强绑定出场实体。
2.  **实现惰性图谱构建 (LazyGraphRAG)**：
    *   废除 `service.py` 里的离线全局社区总结（Community Summaries）构建步骤。在章节落盘时，仅将抽取的新增实体和关系作为悬挂节点增量写入。
    *   **延迟运行时检索 (Query-time Traversal)**：只有当准备撰写新场景并触发 API 时，系统才在运行时以当前出场实体为中心，在图中进行 2-hops 拓扑展开，沿着时序事件 DAG 的有向边**向过去反向游走**，拉取出场实体的最新状态（如判定：John 在第五章已被熔断长剑，当前无法使用），组装为 Fact Constraints 注入 Prompt。
3.  **结合 E2RAG 边元数据进行定点前文召回**：
    *   如果时序图上检索出的关键因果边（如 A 抢夺玉佩）其 source 属性指向了 `Ch2_Scene3.arc`。
    *   系统自动调用 `read_chapter_scene` 提取该特定场景的**微观正文片段**拼入 `context`（伏笔定点爆破拉取），代替原先无脑且存在严重盲区的“前序各章仅保留尾声”机制。

## 💡 建议二：大窗口时代基于 Prompt Caching 的“分层装配”与“自适应角色注入”

### 1. 解决痛点
随着 2026 年中美主流模型支持 256K~2M 的长上下文（可用有效上下文均在 256K 以上），虽然可以把全书设定硬塞进去，但盲目全量注入会导致 Token 费用暴增以及 **Lost in the Middle（注意力在中部溃散）** 造成的人设混淆与 OOC。

### 2. 重构设计
利用主流大模型（Gemini 3.1, Claude 3.5, GPT-5, DeepSeek V4）在 2026 年原生支持的 **Prompt Caching（提示词缓存）** 机制，重构 `context_builder.py` 里的上下文结构：

1.  **静态缓存区 (Static Prefix / System Message)**：
    *   将静态且极少发生改变的世界观文本、完整大纲与大结局描述置于 System Prompt 的开头。
    *   **自适应角色注入 (Ad-hoc Role Selective Ingestion)**：根据当前场景大纲里标记的登场人物 ID，以及从图谱中召回的强关联配角 ID。**仅将这些登场人物的详细 [cid].txt 卡片放入静态缓存区**。其余无关配角卡片直接丢弃，仅留一行名字列表。
    *   由于这个前缀在连续写作多幕时是完全静止且相同的，API 会自动命中缓存（Cache Hit），**缓存计费折减高达 50%~90%，且首 Token 响应延迟大幅降低**。
2.  **动态生成区 (Dynamic Suffix / User Message)**：
    *   将动态变化的“最近一章正文”、“当前场景写作指导（Guidance）”以及由建议一提取的“时序事实硬约束（Fact Constraints）”放在 User Message 的最尾部。
    *   这种设计既确保了静态人设大模型的全量可见，又完全避免了破坏 Prompt Caching 前缀缓存，同时将“当前写作战场”放在最靠近大模型输出的位置，规避了注意力滑移。

## 💡 建议三：推理期 Critic 智能体博弈审计循环 (Critique Loop)

### 1. 解决痛点
解决在正文生成时，由于 LLM 采样温度（Temperature=0.8）的随机性，大模型偶尔会发生无视上下文和约束、自顾自“逻辑神游”的痼疾。

### 2. 重构设计
参考 ConStory-Checker 的双向证据验证思路，在正式的写作管线中引入 `CriticAgent` 的推理期博弈反馈环：

1.  **双向审计流**：在 `Scriptwriter` 执笔流式输出草稿后，后台静默启动 `CriticAgent`。
2.  **事实断言提取与比对**：
    *   `CriticAgent` 将生成的草稿正文提取出微观的原子事实声明（如 `John 挥舞右手`）。
    *   拿这些声明与建议一由图谱中召回的 `Fact Constraints`（如 `John 失去右手`）进行比对校验。
3.  **智能体迭代反馈 (Agent-to-Agent Loop)**：
    *   一旦 Critic 判定发生逻辑冲突，即输出具体的错误原句和修改指示（feedback payload）。
    *   系统拦截此版本不呈送给用户，而是重新唤醒 `Scriptwriter` 传入修改建议进行二次生成。
    *   重试上限限制为 3 次，防止死锁。若审计通过，才正式落盘并异步触发图谱增量更新。
