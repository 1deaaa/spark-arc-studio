# 后端测试目录规范

测试按“守护对象”组织，不按开发任务、缺陷编号或贡献者习惯组织。

仓库中的测试都应当是准备长期维护的正式测试。只服务当前任务、验证通过后即可丢弃的代码属于临时验证，不应进入本目录。

## 目录边界

- `architecture/`：只放跨模块的稳定协议、统一收口层和启动基础设施护栏。
- 领域目录：放具体功能、接口、服务和历史缺陷回归，例如 `chat/`、`director/`、`mcp/`、`projects/`、`story_context/`。
- `conftest.py`：只放确实被多个领域共享的 fixture；领域专用 fixture 放在该领域目录自己的 `conftest.py`。
- 人工维护的样例可放在测试目录；运行时生成的缓存、索引、数据库和导出文件必须写入根目录 `/.tmp/` 或 pytest 的 `tmp_path`。

当前 `architecture/` 只守护以下六类基础能力：

1. Agent 三模态与工具 reference 契约。
2. 工具注册表、统一门面和工具 UI 元数据。
3. Chat NDJSON 事件时序、回放和重试终态。
4. 同步生成器到异步业务流的统一桥接与语义帧。
5. 公共 Patch、Token 分块和数据库迁移基础设施。
6. Matchbox 启动期懒加载。

## 新测试放置流程

1. 先判断它是否需要在未来持续防止回归。若只回答“当前实现是否正常”，按下一节作为临时验证，用完删除。
2. 正式测试先写出被测生产模块或业务能力，例如“用户删除”“图片生成适配器”“聊天压缩”。
3. 查找同领域目录；存在就放进去，不存在就创建语义清晰的目录。
4. 只有测试同时满足以下条件，才允许放入 `architecture/`：
   - 断言跨多个业务模块共享的稳定不变量；
   - 直接守护统一 registry、facade、pipeline、protocol 或公共基础设施；
   - 普通产品需求变化不应频繁修改它。
5. 修复缺陷时，把决定长期保留的回归测试放在缺陷所属领域。缺陷严重或复现困难，不会自动使它成为架构测试。
6. 如果测试主要断言具体提示词措辞、单个供应商参数、单个路由结果、README/Dockerfile 字符串或某次补丁细节，它不是架构测试。

## 临时测试

临时测试包括小范围探针、假设验证、调试输出、一次性数据检查和只为确认本次修复有效而写的脚本。

- 存放：仓库根 `/.tmp/tests/<本次任务>/`，不得放进 `server/test/`。
- 命名：使用 `verify_*.py`、`probe_*.py` 等名称，不使用 `test_*.py`。
- 运行：按文件路径显式执行，不接入 pytest 默认发现、CI 或 coverage。
- 清理：验证结束后立即删除脚本和输出，任务结束前必须清空对应临时目录。
- 升格：若发现值得长期防止复发的行为，重新编写为正式测试并放进所属领域；不要把临时脚本原样迁入。

`/.tmp/` 被 Git 忽略只是防误提交措施，不代表临时测试可以永久堆积。

## 命名规则

- 文件：`test_<能力>.py`，领域目录已经表达层级，不重复堆叠 `architecture`、`contracts`、`regression`。
- 测试函数：`test_<条件>_<预期行为>`，名称应说明行为，不写缺陷编号或“临时测试”。
- 架构测试可以使用 `_contracts` 后缀，但前提是它确实守护长期协议。

## 删除与升格

- 只扫描文档文字、源码字符串或易变提示词整段内容的测试，通常应删除或改为真正的行为测试。
- 重复覆盖同一收口点的页面级/路由级测试应合并，保留最接近真相源的一层。
- 正式领域回归只有在能抽象成跨模块稳定不变量时才能升格到 `architecture/`。
- 不得为了测试通过而直接放宽断言；先判断是实现回归、契约变更、层级错误还是 fixture 过时。

## 运行方式

在 `server` 目录执行：

```bash
# 基础建筑护栏
pytest test/architecture

# 具体领域回归
pytest test/chat test/director

# 全部后端测试
pytest test
```
