# 贡献者版权、来源证明与证据留存说明

生效日期：2026年4月11日

本文档面向 SparkArc 的仓库维护者、代码贡献者、文档贡献者、设计贡献者与第三方部署者，用于说明贡献场景下的版权归属、许可边界、来源证明与证据留存规则。

重要说明：

- 本文件属于项目治理与合规说明，不构成正式法律意见。
- 如存在书面协议、劳动合同、委托开发协议、单独授权协议或贡献者许可协议（CLA），应优先按照该等文件确定权利义务。

## 1. 目的

本文件主要用于说明以下事项：

- 项目贡献场景下的版权归属与许可边界
- 多人协作时如何理解“个人贡献”“合作作品”“汇编性项目”
- 各类贡献者如何保存能够证明原创来源、提交时间与贡献范围的证据
- 在出现来源争议、主体识别争议或知识产权争议时，应优先准备哪些材料

## 2. 贡献者版权的基本原则

在当前仓库未另行引入版权转让协议或单独 CLA 的前提下，项目默认遵循以下基本原则：

1. **贡献者通常保留其原创贡献的著作权。**
2. **贡献被合并进入项目后，并不当然转化为“由某一人单独享有全部版权”。**
3. **项目整体可能同时包含多名贡献者分别享有权利的代码、文档、设计、测试、脚本和素材。**
4. **只有在满足法定“合作作品”条件时，相关作品部分才属于合作作者共同享有。**
5. **如某项内容系对既有作品的改编、翻译、注释、整理或二次加工，其新增表达部分与原作品部分应分别判断权利边界。**

## 3. 如何理解“共享版权”

“共享版权”不是一个足够精确的法律术语。对于开源社区协作，可区分以下三种情况：

### 3.1 各自保有各自贡献的权利

这是最常见的开源协作状态。比如：

- 某贡献者提交了一段新功能代码
- 另一位贡献者补了一份测试
- 第三位贡献者修了一段文档

在没有额外书面约定的情况下，通常按以下原则理解：

- 各自对自己独创完成的部分享有相应权利
- 项目维护者根据项目许可接收、合并、发布这些贡献
- 这不等于全部贡献自动变成“共同共有的一整块版权”

### 3.2 合作作品

如果两人以上共同创作、且贡献难以分割使用，可能构成合作作品。此时：

- 著作权由合作作者共同享有
- 但可分割使用的部分，作者可以单独享有其可分割部分的权利

### 3.3 汇编式项目或持续演进项目

一个长期演进的软件仓库，往往更接近由多个有边界的贡献持续汇聚形成的项目，而不是当然将所有历史提交都视为单一合作作品。

因此，开源仓库通常不将全部历史贡献笼统表述为“共享整个项目版权”，而按以下方式表述：

- “贡献者保留其原创贡献的相应权利”
- “贡献提交并合并后，按项目开源许可授予项目及下游使用者相应使用、修改和分发权”

## 4. 当前仓库的默认表述原则

在当前仓库未另行引入 CLA、DCO、版权转让协议或其他专项书面约定的情况下，贡献版权与许可边界按以下原则表述：

1. 贡献者保留其原创贡献在法律上的相应权利。
2. 向本仓库提交贡献，即表示贡献者确认其有权提交该内容，并同意该贡献按本仓库采用的开源许可进行发布和后续再分发。
3. 除非另有书面约定，项目维护者不因合并贡献而当然取得贡献者原创部分的排他性版权。
4. 任何人不得将他人贡献冒充为自己独立原创，不得篡改署名、来源或提交历史。

上述表述用于统一贡献版权、项目许可与后续再分发的理解边界。

## 5. 进一步统一权利时所需文件

如项目未来需要进一步统一贡献版权或增强项目对外授权稳定性，通常需要单独引入以下机制之一：

- 贡献者许可协议（CLA）
- 开发者来源声明（DCO）
- 版权转让协议
- 雇佣开发、委托开发或专项合作协议

在未采用上述机制之前，公开文档不宜笼统表述“所有贡献自动归项目方所有”。

## 6. 仓库贡献版权政策示例文本

仓库贡献指南可采用以下表述：

> 除非另有书面约定，贡献者保留其原创贡献在法律上的相应权利。向本仓库提交 Pull Request、补丁、文档、设计稿、脚本或其他贡献，即表示贡献者确认其有权提交该内容，并同意该贡献按本仓库当前适用的开源许可进行发布、合并与再分发。

该表述用于同时明确贡献者权利、项目发布依据与下游许可来源。

## 7. 所有贡献者的基础证据范围

无论是维护者还是普通贡献者，均宜保留以下基础证据：

1. **创作过程证据**
   - 本地草稿、分支记录、设计稿、思路说明
   - 编辑历史、草图、原始素材、测试记录
2. **提交与评审证据**
   - Commit 记录、签名提交、签名 Tag
   - Pull Request、Issue、Review 评论、讨论记录
3. **时间与发布证据**
   - Release 页面、构建日志、制品上传记录
   - 文档发布时间、截图、演示视频
4. **来源与授权证据**
   - 外部素材来源
   - 授权许可文本
   - 第三方依赖和资源的许可证信息

## 8. 维护者的项目级证据范围

项目维护者宜额外保留以下内容：

- 仓库创建时间与最早公开提交
- 各版本 release 包与对应源码快照
- CI 产物哈希、构建日志与发布日期
- 官方实例名单、域名、页面截图、版本号与提交哈希
- 关键文档、路线图、设计说明与法律声明的发布时间

## 9. 贡献来源合规要求

贡献者在提交内容前，应至少确认：

- 贡献内容由本人原创，或已获得合法授权
- 未直接复制粘贴受限制代码、设计稿、文档、图像或商业素材
- 未将受雇、受托项目中的专有成果未经许可转入本仓库
- 未删除原作者署名、版权标识、许可文本或来源说明

## 10. 争议处理中通常应优先准备的材料

如出现版权归属、贡献来源、页面来源、项目名称使用、品牌识别或实例关联方面的争议，通常应优先准备：

- 对应提交记录与分支历史
- PR、Issue、Review 与合并记录
- 草稿、设计稿、演示文件与本地创作痕迹
- 版本发布时间与构建产物
- 页面截图、导出文件、实例指纹与公开说明
- 域名、备案主体、发布账号或运营主体信息
- 外部素材授权证明与许可证文本

## 11. 主要法律依据

以下条次为本文件的主要法律依据：

- 《中华人民共和国著作权法》第11条：著作权属于作者，但法律另有规定的除外。
- 《中华人民共和国著作权法》第12条：在作品上署名的自然人、法人或者非法人组织，在无相反证明的情况下，推定为作者或者其他著作权人。
- 《中华人民共和国著作权法》第13条：改编、翻译、注释、整理已有作品而产生的作品，其著作权由相应创作人享有，但行使著作权时不得侵犯原作品的著作权。
- 《中华人民共和国著作权法》第14条：两人以上合作创作的作品，著作权由合作作者共同享有；没有参加创作的人，不能成为合作作者。
- 《最高人民法院关于民事诉讼证据的若干规定》第14条：电子数据包括网页、博客、微博客、通信信息、注册信息、交易记录、登录日志、文档、图片、音频、视频、计算机程序等。
- 《最高人民法院关于民事诉讼证据的若干规定》第15条：电子数据原件、与原件一致的副本以及直接来源于电子数据的可识别输出介质，均可作为原件认定基础。
- 《最高人民法院关于民事诉讼证据的若干规定》第23条：人民法院调查收集视听资料、电子数据，应当要求被调查人提供原始载体；提供复制件的，应说明来源和制作经过。
- 《最高人民法院关于民事诉讼证据的若干规定》第25条至第29条：当事人或者利害关系人可以依法申请证据保全，人民法院可以采取查封、扣押、录音、录像、复制、鉴定、勘验等方式固定证据。

## 12. 仓库治理取向

从项目治理角度，当前仓库采用以下取向：

- 对贡献者使用“保留原创贡献权利 + 按项目许可发布”的表述
- 不轻易使用“共享版权”“全部归项目方所有”这类容易引起误解的说法
- 尽快补充贡献版权政策，必要时再决定是否引入 CLA 或 DCO
- 对核心版本、核心页面、核心设计与关键发布动作持续留存可验证证据
